# 모두의 뇌 PRD

## 1. 문서 목적

이 문서는 모두의 뇌 MVP를 개발하기 위한 제품 요구사항을 정리한다. 기획서가 서비스 방향을 설명한다면, PRD는 사용자가 겪는 문제, MVP 범위, 핵심 기능, 성공 기준을 개발 가능한 수준으로 정의한다.

## 2. 제품 한 줄 정의

모두의 뇌는 회의록, 연구 메모, 팀 피드백에 흩어진 프로젝트 맥락을 AI가 구조화해 팀 전체가 함께 쓰는 공유 지식망으로 보여주는 협업 맥락 에이전트이다.

## 3. 문제 정의

팀 프로젝트에서는 회의 내용, 결정 이유, 역할별 관점, 남은 질문이 여러 문서와 메신저에 흩어진다. 시간이 지나면 팀원은 이전 결정을 다시 설명하거나, 같은 자료를 다시 찾거나, 서로 다른 이해를 바탕으로 작업하게 된다.

### 핵심 문제

- 문서와 회의록은 남아 있지만 결정 배경이 사라진다.
- 팀원마다 같은 용어와 목표를 다르게 이해한다.
- 새로 합류한 사람이 프로젝트 맥락을 빠르게 따라가기 어렵다.
- 회의 요약은 할 일을 정리할 수 있지만, 관점 차이와 미결 질문을 연결해주지는 못한다.

## 4. 목표 사용자

| 사용자 | 상황 | 주요 니즈 |
| --- | --- | --- |
| 팀 프로젝트 팀장 | 회의 후 내용을 정리하고 공유해야 함 | 팀원이 같은 맥락을 이해하게 만들기 |
| 공모전/해커톤 팀원 | 짧은 기간에 많은 결정을 내려야 함 | 결정 이유와 남은 질문을 빠르게 확인하기 |
| 연구 프로젝트 참여자 | 여러 사람이 같은 주제를 나눠 조사함 | 각자의 관점과 자료를 연결하기 |
| 새로 합류한 팀원 | 이전 회의와 문서를 처음부터 읽어야 함 | 지금까지의 흐름을 빠르게 파악하기 |

## 5. 제품 목표

- 팀 문서에서 핵심 주제, 용어, 결정사항, 관점 차이, 미결 질문을 추출한다.
- 추출한 정보를 사람/역할/주제/질문 단위로 연결해 보여준다.
- 새 참여자가 프로젝트의 배경과 현재 상태를 빠르게 이해할 수 있게 한다.
- 회의 요약 도구가 아니라 협업 맥락 공유 도구로 차별화한다.

## 6. MVP 범위

### 포함

- 텍스트 기반 문서 입력
- 예시 데이터 불러오기
- AI 분석 결과 표시
- 프로젝트 맥락 요약
- 참여자별 관점 표
- 미결 질문 목록
- 공유 지식맵 시각화
- 새 참여자 온보딩 요약

### 제외

- 메신저/문서 도구 자동 연동
- 실시간 회의 녹음
- 팀 권한 관리
- 파일 업로드 파싱
- 자동 의사결정
- 실제 배포 인증/결제 기능

## 7. 핵심 사용자 흐름

1. 사용자가 프로젝트 이름을 입력한다.
2. 회의록, 연구 메모, 팀 피드백을 텍스트로 붙여넣는다.
3. 사용자가 `맥락 분석하기`를 누른다.
4. AI가 프로젝트 맥락을 구조화한다.
5. 사용자는 요약, 관점 표, 미결 질문, 지식맵을 확인한다.
6. 사용자는 새 팀원에게 온보딩 요약을 공유한다.

## 8. 핵심 기능 요구사항

### 8.1 문서 입력

- 프로젝트 이름은 2자 이상 120자 이하를 허용한다.
- 사용자는 긴 텍스트를 붙여넣을 수 있어야 한다.
- 최소 120자, 최대 20,000자의 입력을 허용한다.
- 빈 입력 상태에서는 분석 버튼을 비활성화한다.
- 예시 입력을 한 번에 불러올 수 있어야 한다.

### 8.2 맥락 추출

- AI는 다음 항목을 추출해야 한다.
  - 핵심 주제
  - 중요한 용어
  - 결정사항
  - 결정 배경
  - 참여자별 관점
  - 이해가 갈린 지점
  - 미결 질문

### 8.3 공유 지식맵

- 결과는 노드와 연결 관계로 표현할 수 있어야 한다.
- 노드 타입은 `topic`, `person`, `role`, `decision`, `question`을 기본으로 한다.
- 연결 관계에는 짧은 설명이 있어야 한다.

### 8.4 온보딩 요약

- 새 참여자가 먼저 알아야 할 내용을 5줄 이내로 보여준다.
- 현재 결정된 것과 아직 결정되지 않은 것을 분리한다.
- 다음 회의에서 확인해야 할 질문을 포함한다.

### 8.5 팀원별 관점 에이전트

- 각 팀원의 발언, 역할, 우선순위, 우려를 입력 기록에서 근거 기반으로 추출한다.
- 팀원별 결과는 성격 추정이 아니라 `프로젝트 관점`으로 표현한다.
- 동일한 결정에 대해 어떤 팀원은 사용자 흐름을, 어떤 팀원은 구현 범위를, 어떤 팀원은 발표 차별점을 중시하는지 비교한다.
- 공유 에이전트는 팀원별 관점을 종합해 합의 지점, 충돌 지점, 다음 질문을 만든다.
- MVP에서는 별도 자율 에이전트가 아니라 구조화된 다중 프롬프트 또는 병렬 분석 결과로 시작한다.

## 9. 비기능 요구사항

- 결과는 10초 이내에 표시되는 것을 목표로 한다.
- AI 응답 실패 시 사용자가 다시 시도할 수 있어야 한다.
- 개인정보가 포함될 수 있으므로 민감 정보 입력 주의 문구를 제공한다.
- 모바일 화면에서도 결과 카드가 깨지지 않아야 한다.
- 분석 결과는 JSON 구조를 기준으로 렌더링한다.

## 10. 성공 지표

| 지표 | 목표 |
| --- | --- |
| 사용자가 서비스 목적을 이해하는 시간 | 1분 이내 |
| 예시 입력으로 결과 확인까지 걸리는 시간 | 30초 이내 |
| 팀원이 설명할 수 있는 핵심 차별점 | 회의 요약이 아니라 맥락 공유 |
| MVP에서 반드시 보이는 결과 | 요약, 관점 표, 미결 질문, 지식맵 |

## 11. 우선순위

| 우선순위 | 항목 |
| --- | --- |
| P0 | 문서 입력, 예시 입력, 더미 분석 결과 화면 |
| P0 | 맥락 요약, 관점 표, 미결 질문 표시 |
| P1 | 지식맵 노드/링크 시각화 |
| P1 | LLM API 연동 |
| P1 | 팀원별 관점 에이전트 결과 스키마 |
| P2 | 결과 저장, 공유 링크, 히스토리 |

## 12. 리스크

- AI가 결정사항과 의견을 혼동할 수 있다.
- 입력 문서가 짧으면 맥락 추출 품질이 낮아질 수 있다.
- 지식맵이 복잡해지면 오히려 이해하기 어려울 수 있다.
- 팀 문서에는 개인정보가 들어갈 수 있으므로 입력 안내가 필요하다.
- 팀원별 관점 분석이 성격 추정처럼 보이면 신뢰와 개인정보 측면의 문제가 생길 수 있다.

## 13. 다음 단계

- TRD 기준으로 데이터 구조와 화면 컴포넌트를 확정한다.
- 프롬프트 디자인 문서 기준으로 LLM 응답 JSON 스키마를 고정한다.
- 더미 데이터로 입력 화면과 결과 화면을 먼저 구현한다.
